# 手机端空间体验触发与发布生效方案

> 版本：v1.0
> 日期：2026-10-02
> 适用项目：`xiyou-ar / 造梦 · 故事空间 AR 空间编辑器`
> 结论：可以实现，但需要把当前“编辑器试玩/本地发布快照”升级为“游客 Runtime + 持久化发布版本”

---

## 1. 结论先行

### 1.1 推荐的第一版方案

推荐采用：

```text
二维码进入体验
  → 打开手机 Web Runtime
  → 用户点击“开始体验”并授权相机/方向/定位
  → 二维码或 VPS 完成空间定位
  → 加载指定 Release 发布包
  → 用户在真实空间中点击、注视、按住或进入区域触发互动
```

二维码既可以承担“打开体验”的作用，也可以承担“空间校准锚点”的作用。对于入口、展板、文物牌、打卡点等固定位置，这是成本最低、最容易解释、最容易现场验收的方案。

### 1.2 不建议把“到达地点后自动打开网页”作为 Web 端默认能力

手机浏览器通常不能在用户没有操作的情况下：

- 自动打开一个网页；
- 自动开启摄像头；
- 自动获取精确位置；
- 在后台持续运行空间识别；
- 直接把用户带入 AR 体验。

因此，“到了指定地点自动触发”应拆成两个问题：

1. **如何让用户进入 Runtime**：扫码、NFC、短链接、App/小程序入口；
2. **Runtime 打开以后如何触发内容**：GPS 粗定位、QR/图像锚点、VPS 或相机位置进入区域。

在 Web MVP 中，推荐定义为：

> 用户先通过扫码或链接打开 Runtime；当 Runtime 处于前台并完成定位后，用户进入配置区域时自动触发内容。

如果要求手机锁屏、浏览器后台也能收到地理围栏通知，或者完全无人操作地拉起体验，则需要原生 App、小程序或系统级地理围栏能力，不能只依赖普通 Web 页面。

### 1.3 当前“发布”不会让另一台手机实时看到新对象

当前编辑器中的“发布”主要完成：

- 发布检查；
- 在 `scene.meta.releases` 中创建不可变快照；
- 将快照保存在当前场景数据中。

当前 `runtime.html?room=demo` 读取的是**当前浏览器的 `localStorage`**。因此：

- 同一浏览器、同一来源下，试玩/Runtime 可能读到本机保存的场景；
- 另一台手机没有编辑器浏览器的 `localStorage`，无法读到这个场景；
- Yjs 协作同步的是编辑草稿，不是游客 Runtime 的发布通道；
- 点击“发布”不会自动把新对象推送给已经打开的游客手机。

要实现真正的游客发布，需要增加：

```text
编辑器 Draft
  → 发布检查
  → 生成 Release
  → 上传 scene manifest 和资产
  → CDN / Runtime API 提供稳定地址
  → 游客 Runtime 按 releaseId 加载
```

## 2. 先区分三个界面

当前项目中“试玩”容易和“用户端界面”混淆，建议在产品和文档中明确区分。

| 界面 | 当前入口 | 服务对象 | 是否是正式游客端 |
|---|---|---|---|
| 创作模式 | 编辑器顶栏“创作” | 场景设计师、运营人员 | 否 |
| 编辑器试玩 | 顶栏“试玩”、Viewport Play HUD | 编辑人员验收交互逻辑 | 否，是模拟预览 |
| 游客视角模拟 | 编辑器内 `arview.js` | 编辑人员检查相机、方向和点击 | 否，是编辑器内覆盖层 |
| 游客 Runtime | `editor/runtime.html` | 手机游客、现场体验者 | 是，正式运行时入口 |

### 2.1 “试玩”是什么

编辑器试玩的价值是验证：

- 节点顺序是否正确；
- 对象是否显示在预期位置；
- `tap / gaze / hold / enter` 是否触发；
- 时间线、卡片、奖励、显隐是否生效；
- 发布前是否存在明显问题。

它运行在编辑器上下文中，仍然带有编辑器的场景、状态和调试能力。因此它不是游客最终看到的界面。

### 2.2 `runtime.html` 才是用户端的方向

当前 `editor/runtime.html` 和 `editor/src/runtime/main.js` 已经具备正式 Runtime 的雏形：

- 独立于编辑器 UI；
- 移动端安全区布局；
- 相机背景和无相机预览；
- 方向传感器与拖拽视角；
- WebXR 能力探测；
- QR/BarcodeDetector 探测；
- GPS 粗定位；
- VPS `/localize` 接口预留；
- 发布场景的对象、底座、区域和互动加载；
- `tap / gaze / hold / enter` 触发；
- 时间线、卡片、奖励、高亮、显隐和节点跳转。

但它目前更接近“可运行的 Runtime 原型”，还不是完整的线上游客交付链路。缺口主要是发布包持久化、资源 CDN、跨设备访问、真实锚点定位和发布版本切换。

## 3. 手机端如何触发体验

### 3.1 方案对比

| 方案 | 适合场景 | 优点 | 主要限制 | 建议级别 |
|---|---|---|---|---|
| 扫二维码打开体验 | 入口、展板、文物牌、打卡点 | 成本低、用户理解成本低、Web 兼容性好 | 需要用户扫码和点击开始 | **MVP 首选** |
| NFC 标签 | 入口、导览牌、近距离触碰点 | 比扫码更自然，可写入短链接 | 设备、浏览器和系统行为存在差异，仍需用户确认 | MVP 后增强 |
| 链接/短链接 | 公众号、活动页、工作人员分发 | 传播方便，可统计来源 | 链接本身不能精确定位用户 | **必须支持** |
| GPS 地理围栏 | 室外景区、路线导览 | 可判断用户接近某个大区域 | 精度通常是米级到几十米；浏览器不能保证后台唤起 | 作为粗定位/兜底 |
| QR/图像锚点 | 固定展板、入口标识、室内点位 | 位置和方向可控，适合空间对齐 | 需要用户将相机对准标识 | **MVP 定位首选** |
| VPS / 视觉定位 | 景区、建筑、复杂空间 | 不需要每个点位都放二维码，空间体验自然 | 需要真实采集、服务端和设备适配，部署复杂 | P1 |
| 蓝牙 Beacon | 大型场馆、室内导航 | 可做近距离区域判断 | 浏览器支持和后台能力不稳定，通常需要 App | 不作为 Web 首选 |
| 原生 App / 小程序 | 长期运营、通知、后台定位 | 权限、推送、地理围栏和设备能力更完整 | 开发和分发成本高 | P2 |

### 3.2 推荐的触发层级

不要只选择一种触发方式，而是把入口和定位设计成可降级的链路：

```text
体验入口
├─ QR 扫码
├─ NFC / 短链接
└─ App / 小程序深链（后续）

空间定位
├─ VPS 精定位
├─ QR / 图像锚点
├─ WebXR 平面/空间能力
├─ GPS 粗定位
└─ 手动参考点

内容触发
├─ 用户点击对象
├─ 注视对象达到指定时长
├─ 按住对象达到指定时长
├─ 进入空间区域
└─ 时间线 / 剧情节点事件
```

入口失败不应阻断体验。比如用户从短链接进入但 VPS 不可用时，可以提示扫描附近的二维码；GPS 只有粗定位时，可以展示“已到达景区，请对准入口标识完成校准”。

## 4. 推荐用户流程

### 4.1 流程 A：扫码进入并立即体验

适合第一个可交付版本。

```text
用户扫描入口二维码
  ↓
打开短链接 /runtime.html?experience=xxx&entry=gate-01
  ↓
Runtime 加载 Release manifest
  ↓
用户点击“开始体验”
  ↓
申请相机、方向和位置权限
  ↓
使用当前二维码或 VPS 校准坐标
  ↓
加载底座和互动资产
  ↓
用户点击/注视/按住虚拟对象
  ↓
触发剧情、动画、卡片或奖励
```

二维码不应直接编码整份 JSON，建议只编码短链接和入口信息，例如：

```text
https://体验域名/xiyou/runtime.html
  ?experience=huaguoshan
  &release=latest
  &entry=gate-01
  &anchor=qr-gate-01
```

生产环境建议将长参数收敛为短码：

```text
https://xj.example.com/e/7K3M9P
```

服务端根据短码返回体验、版本、入口、锚点和运行时配置。

### 4.2 流程 B：打开链接，到达地点后触发

适合活动页、公众号、现场工作人员分发链接。

```text
用户点击体验链接
  ↓
打开 Runtime，用户点击“开始体验”
  ↓
获取位置权限并开始 watchPosition
  ↓
先用 GPS 判断是否接近景区/区域
  ↓
提示用户“请继续前往：虚境入口”
  ↓
进入指定区域，触发 enter 事件
  ↓
如需精确叠加，再要求扫描 QR 或执行 VPS 定位
```

这里的“自动触发”是指：

> Runtime 已打开、定位已授权、页面处于前台时，用户进入区域后自动触发。

不是指：

> 用户手机锁屏或没有打开网页时，浏览器自动打开网页并开始 AR。

GPS 不适合直接决定虚拟物体的厘米级空间位置。它只适合判断“是否到达某个大区域”，精确叠加应使用 QR/图像锚点或 VPS。

### 4.3 流程 C：NFC 或小程序入口

可以将 NFC 标签写入和二维码相同的短链接。用户碰一下标签后，仍然进入同一个 Runtime 和 Release 系统。

这样可以让入口协议统一：

```text
QR / NFC / 短链接 / 小程序深链
              ↓
        Experience Resolver
              ↓
        同一个 Runtime
```

不要为 QR、NFC 和链接分别维护三套场景加载逻辑。

## 5. 空间定位与触发的技术边界

### 5.1 坐标系必须统一

编辑器中的对象位置是场景本地坐标；手机端需要将手机姿态转换到同一个坐标系，才能保证方块、角色和粒子出现在真实空间中的正确位置。

建议发布包明确保存：

```json
{
  "coordinateSystem": {
    "up": "Y",
    "forward": "-Z",
    "handedness": "right",
    "units": "meters",
    "origin": "site-local"
  },
  "anchors": [
    {
      "id": "qr-gate-01",
      "kind": "qr",
      "worldPose": {
        "position": [0, 0, 0],
        "rotation": [0, 0, 0]
      },
      "markerSizeMeters": 0.18
    }
  ]
}
```

### 5.2 各类定位能力的职责

| 能力 | 能解决什么 | 不能解决什么 |
|---|---|---|
| GPS | 判断用户是否接近某个景区或大区域 | 不保证虚拟物体和真实建筑精确重合 |
| QR / 图像锚点 | 建立入口或点位的局部坐标和方向 | 用户需要看见并扫描标识 |
| WebXR | 提供设备 AR 会话、相机和部分平面能力 | 不等于自动知道景区坐标，也不统一支持 VPS |
| VPS | 将相机图像匹配到预先采集的真实空间 | 需要采集数据、服务端和稳定光照/纹理 |
| 手动参考点 | 演示和定位失败时提供可用兜底 | 精度和重复性有限 |

### 5.3 `enter` 触发需要什么

`enter` 触发至少需要：

1. Runtime 已启动；
2. 手机位置或姿态已经转换到场景坐标；
3. 场景中配置了触发区域或目标对象半径；
4. Runtime 持续更新相机/设备位置；
5. 进入状态从 `false` 变为 `true`。

仅有 GPS 经纬度不能直接判断高斯场景坐标中的局部区域，除非发布包同时维护了经纬度到 site-local 坐标的转换关系。室内和小范围体验应优先使用 QR/VPS。

## 6. 编辑器“发布”与游客端生效

### 6.1 需要区分 Draft、Release 和 Runtime Session

```text
Draft
├─ 编辑器正在修改的草稿
├─ 可被 Yjs 协作者实时看到
└─ 不应直接暴露给游客

Release
├─ 经过检查的不可变发布快照
├─ 绑定资源版本、底座版本、锚点和 Runtime 配置
└─ 游客端加载的稳定版本

Runtime Session
├─ 某一个游客当前打开的运行实例
├─ 有自己的剧情进度和触发状态
└─ 默认不被编辑器草稿直接改写
```

核心原则：

> 实时协作解决“团队如何一起改草稿”；发布系统解决“游客拿到哪个稳定版本”。两者不能混为一谈。

### 6.2 推荐的发布流程

```text
编辑器修改方块
  ↓
本地变更 / Yjs 同步到 Draft
  ↓
编辑器内试玩
  ↓
点击“预览”执行检查
  ↓
点击“发布”
  ↓
服务端再次校验权限、引用、资产、坐标和设备预算
  ↓
创建 release_id 和不可变 manifest
  ↓
上传/确认场景资产和底座 CDN 地址
  ↓
更新 Experience 的 active_release 指针
  ↓
游客新建 Session 时加载新版本
```

发布的最小产物建议包括：

```text
release/
├─ manifest.json
├─ scene.json 或 scene.json.gz
├─ asset-manifest.json
├─ anchors.json
├─ runtime-profile.json
├─ checks.json
└─ 资产 CDN 引用
```

不要把高斯底座、视频和模型二进制直接塞进 Yjs 或场景 JSON。发布包只保存稳定 URL、哈希、版本和元数据。

### 6.3 建议的数据结构

```json
{
  "experienceId": "exp_huaguoshan",
  "releaseId": "rel_20261002_0007",
  "version": 7,
  "status": "published",
  "publishedAt": "2026-10-02T10:30:00.000Z",
  "sceneUrl": "https://cdn.example.com/releases/rel_20261002_0007/scene.json",
  "assetManifestUrl": "https://cdn.example.com/releases/rel_20261002_0007/assets.json",
  "activeEntry": "gate-01",
  "runtime": {
    "minVersion": "0.1.0",
    "supports": ["mobile-web", "webxr"],
    "locationMode": "qr-or-vps",
    "allowManualFallback": true
  },
  "integrity": {
    "sceneSha256": "...",
    "assetManifestSha256": "..."
  }
}
```

编辑器当前的 `scene.meta.releases` 可以继续作为本地历史和恢复入口，但正式发布应由服务端保存 release 记录，不能只依赖浏览器存储。

## 7. “发布后实时出现”应该怎么定义

### 7.1 三种生效模式

| 模式 | 访客何时看到方块 | 实现复杂度 | 推荐用途 |
|---|---|---:|---|
| 新会话生效 | 新打开或刷新 Runtime 后看到 | 低 | **默认 MVP** |
| 当前会话提示更新 | 已打开页面收到新版本通知，用户点击刷新/重新加载 | 中 | 运营更新、活动现场 |
| 当前会话热更新 | 已打开页面自动接收增量并出现方块 | 高 | 小型互动事件、临时运营 |

### 7.2 推荐的默认语义

点击发布后：

- 新游客打开体验：立即拿到新 `active_release`；
- 已经打开的游客：继续使用当前 Session 的版本；
- 如果 Runtime 监听到新版本：显示“场景有新版本，重新加载体验”；
- 不自动打断游客正在进行的剧情、定位和奖励流程；
- 运营人员可以选择“立即更新”或“下次会话生效”。

这是比“所有手机立刻强行出现方块”更安全的语义，因为：

- 游客当前可能已经完成一半剧情；
- 新版本可能改变对象位置和触发器；
- 大模型、视频或底座可能仍在 CDN 缓存；
- 发布版本需要可回滚、可审计和可复现。

### 7.3 真正实时更新的适用边界

如果要做到当前手机自动出现新方块，建议只对**安全的增量内容**开放：

```text
允许热更新：
- 图片/文案/卡片内容
- 对象显示/隐藏
- 简单位置和动画参数
- 活动开关、奖励文案

默认不热更新：
- 高斯底座
- 坐标系和锚点
- Collider
- 大视频和 GLB
- 已运行剧情的节点拓扑
- 权限、支付和奖励规则
```

实现方式可以是：

```text
Runtime 启动时 GET /experiences/:id/active-release
Runtime 每 30～60 秒轮询，或保持 SSE/WebSocket
服务端发布后更新 active_release
Runtime 收到 release_changed
  → 比较内容能力和当前版本
  → 安全增量则应用
  → 否则提示刷新
```

不建议让游客 Runtime 直接订阅 Yjs Draft。这样会导致未审核内容、协作者半成品和临时资源直接暴露给用户，也会破坏回滚和版本追踪。

## 8. 当前代码与目标方案的对应关系

### 8.1 已有基础

当前项目已经有不少可复用能力：

- `editor/src/runtime/main.js`：独立游客 Runtime、对象和底座加载、触发器、时间线；
- `editor/runtime.html`：Runtime 页面入口；
- `editor/src/ui/arview.js`：编辑器内相机/陀螺仪/点击模拟；
- `editor/src/core/schema.js`：`anchors`、`zones`、`triggers`、发布检查；
- `editor/src/core/store.js`：`createRelease()`、发布快照、恢复和差异；
- `editor/src/ui/topbar.js`：试玩、游客 Runtime、预览、发布入口；
- `editor/src/core/collab.js`：Draft 的 Yjs 协作；
- `README.md` 已定义 `runtime.html?scene=...&release=...` 的外部场景加载方向。

### 8.2 当前最关键的缺口

| 缺口 | 当前状态 | 影响 |
|---|---|---|
| 跨设备场景读取 | `room` 路径依赖本机 `localStorage` | 手机无法读取编辑器电脑的场景 |
| 正式 Release API | `createRelease()` 主要在本地场景中保存快照 | 无法让游客按版本稳定加载 |
| 资产持久化 | 发布检查可阻止临时 URL，但没有完整上传/部署链路 | 另一台设备无法访问 `blob:`/`local:` 资源 |
| active release | 没有服务端当前生效版本指针 | 无法实现“发布后新访客自动拿新版本” |
| Runtime 更新通知 | 当前没有完整 release polling/SSE/WebSocket | 已打开手机不会知道有新版本 |
| 真实二维码定位 | 当前有 BarcodeDetector 探测方向，但需补入口、识别结果和坐标对齐 | 扫到二维码不等于已完成空间校准 |
| 真实 VPS | 只有 `?localize=` 接口预留 | 需要部署模型、服务和坐标转换验收 |
| 服务端权限 | 前端发布检查不能替代服务端校验 | 生产发布需要鉴权、审计和回滚 |

### 8.3 当前 `room` 的定位

`room` 更适合表示：

- 编辑器协作房间；
- Demo 场景隔离；
- 黑客松现场协作。

不建议把它作为长期游客访问 ID。正式 Runtime 应使用：

```text
experienceId + releaseId + entryId + sessionId
```

## 9. 推荐的 MVP 产品方案

### 9.1 用户端

第一版只做一条清晰链路：

1. 运营人员在编辑器完成场景；
2. 点击“预览”，在编辑器试玩；
3. 点击“发布”；
4. 服务端生成 `releaseId`，上传 manifest 和资源；
5. 编辑器生成“游客体验二维码”；
6. 用户扫码打开 Runtime；
7. 点击开始并授权相机；
8. 扫描入口二维码/图像锚点完成校准；
9. 进入区域后触发互动；
10. 新版本发布后，新会话加载新版本，旧会话收到更新提示。

### 9.2 第一版不做

- 浏览器后台自动拉起体验；
- 仅靠 GPS 完成精确 AR 对齐；
- 直接把 Yjs Draft 推送给游客；
- 复杂的游客账号体系；
- 所有对象的无条件热更新；
- 以高斯点云直接充当可靠碰撞体；
- 通过二维码携带整份场景 JSON 或大文件。

### 9.3 编辑器中的建议交互

在“发布结果”中增加清晰的游客交付区：

```text
发布成功 · v7

游客入口
[打开游客 Runtime] [复制链接] [生成二维码]

定位方式
[QR / 图像锚点] [VPS] [GPS 兜底]

版本策略
● 新会话立即生效
○ 已打开会话提示更新
○ 允许安全内容热更新

[查看发布包] [复制 Release ID] [回滚到上一版本]
```

在 Runtime 中显示：

```text
故事空间 · 花果山觉醒
版本 v7
定位：已通过入口标识校准
[开始体验]
```

不要让游客看到 `room`、Yjs、Draft、对象 ID、调试日志等编辑器概念。

## 10. 实施拆分

### Phase 1：跨设备可访问的发布闭环

目标：另一台手机能打开并看到已发布场景。

- 增加 `POST /experiences/:id/releases`；
- 保存 release manifest 和 scene snapshot；
- 资产上传到对象存储/CDN；
- Runtime 支持 `experienceId` 和 `releaseId`；
- `latest` 解析为服务端 `active_release`；
- 二维码生成和复制链接；
- 服务端发布前重复执行校验；
- 验收：编辑器电脑发布一个方块，手机扫码后能看到。

### Phase 2：可靠空间定位

目标：方块在真实空间中位置稳定。

- QR/图像锚点的 ID、物理尺寸和世界 Pose；
- 扫描结果与 `entryId/anchorId` 绑定；
- 站点坐标系和锚点转换；
- GPS 作为区域级兜底；
- 手动参考点作为演示兜底；
- 验收：不同手机从同一入口进入，能在允许误差内对齐。

### Phase 3：发布变更通知

目标：已打开 Runtime 的游客知道有新版本。

- Runtime 轮询或 SSE；
- `release_changed` 事件；
- 默认提示用户刷新；
- 记录 Runtime 当前 `releaseId`；
- 回滚后新会话恢复旧版本；
- 验收：编辑器发布 v8，已打开手机看到更新提示，新打开手机直接拿到 v8。

### Phase 4：受控热更新

目标：支持活动期间小范围内容即时变化。

- 对象显隐、文案、卡片和动画参数的增量补丁；
- 增量补丁 schema 和白名单；
- 热更新前后兼容性检查；
- 大资源、底座、锚点变更仍提示刷新；
- 验收：发布一个安全增量，当前 Runtime 在不中断定位的情况下更新。

### Phase 5：原生能力增强

仅当产品需要后台通知、长期用户身份、系统地理围栏或更稳定 AR 能力时考虑：

- PWA 安装；
- 原生 App 或小程序；
- 推送通知；
- 系统地理围栏；
- Beacon/NFC 深链；
- 设备能力和账号体系管理。

## 11. 验收标准

### 入口

- [ ] QR、短链接和 NFC（如启用）都能解析到同一个 Experience Resolver；
- [ ] 用户不会看到编辑器房间名和 Draft 信息；
- [ ] 首次进入有明确的开始按钮和权限说明；
- [ ] 无相机、无陀螺仪、无 GPS 时仍有可解释的降级路径。

### 定位

- [ ] GPS 只用于粗定位，不宣称厘米级 AR 对齐；
- [ ] QR/图像锚点有 ID、物理尺寸、坐标和版本；
- [ ] VPS 返回的坐标系和编辑器坐标系经过实机验收；
- [ ] 定位失败时给出下一步动作，而不是显示“加载成功”。

### 发布

- [ ] 发布版本具有不可变 `releaseId`；
- [ ] 场景 JSON、资产和底座均是跨设备可访问的持久化 URL；
- [ ] `blob:`、`local:` 等临时 URL 不能进入正式 Release；
- [ ] 发布包记录检查结果、版本、发布人、时间和依赖版本；
- [ ] 可以查看、恢复和回滚历史版本。

### 生效

- [ ] 新会话按 `active_release` 加载；
- [ ] 已打开会话不会被未经确认的结构性变更强制打断；
- [ ] 发布变更可通过轮询、SSE 或 WebSocket 通知；
- [ ] 热更新只允许白名单内容；
- [ ] 编辑器 Draft 不会直接暴露到游客端。

### 端到端验收场景

```text
编辑器电脑：添加一个蓝色方块 → 预览 → 发布 v2
手机 A：扫码 → 开始体验 → 校准 → 看到蓝色方块
编辑器电脑：将方块改为红色并发布 v3
手机 B：重新扫码 → 直接看到红色方块
手机 A：收到“有新版本”提示 → 用户确认后更新
编辑器电脑：回滚到 v2
手机 C：重新进入 → 加载 v2
```

## 12. 最终建议

当前项目不需要在“扫码、链接、自动触发、试玩、发布”之间做单选。更合理的产品结构是：

```text
扫码 / 链接 / NFC：负责进入体验
QR / VPS / WebXR / GPS：负责定位和对齐
tap / gaze / hold / enter：负责触发内容
编辑器试玩：负责创作者验收
Release + Runtime：负责游客交付
Yjs Draft：负责团队协作，不直接服务游客
```

最终建议可以概括为：

> **第一阶段做“扫码进入 + QR 校准 + Web Runtime + Release 发布”；第二阶段做“VPS 精定位 + 已打开会话更新提示”；第三阶段再做“受控热更新和 App/小程序后台能力”。**

因此，用户提出的整体方案是可实现的，但当前代码已经完成的是 Runtime 原型和本地发布快照，尚未完成跨设备正式发布。下一步最有价值的工作不是继续增加试玩按钮，而是补齐“发布服务、持久化资产、二维码入口、锚点对齐和版本生效策略”这条端到端链路。

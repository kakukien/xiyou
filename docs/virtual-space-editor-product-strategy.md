# 虚拟空间场景编辑器产品升级方案

> 版本：v1.1
>
> 分析对象：`xiyou-ar / 造梦 · 故事空间 AR 空间编辑器`
>
> 分析视角：编辑器产品、景区资源复用、跨项目协同、交互内容生产、设计系统
>
> 当前分支：`codex/product-strategy-editor`

---

## 1. 结论先行

当前项目已经完成了一个很有价值的“空间内容创作工作台”雏形，而不是简单的 Three.js Demo：

- 有完整的场景数据模型：场景基底、对象、素材、时间线、触发器、剧情节点、锚点。
- 有接近 UE 的编辑器工作流：Outliner、Viewport、Details、Content Browser、Timeline、试玩模式。
- 已经具备 AI 场景编辑、Yjs 实时协作、预算检查、发布检查、游客视角、锚点和高斯底座接入方向。
- 当前最重要的突破口不是继续堆“更多物体类型”或“更多特效”，而是把项目从**单场景编辑器**升级为**景区空间内容生产与运营平台**。

建议的产品定位：

> 面向景区、文旅集团和数字内容服务商的空间体验生产平台：把高斯重建的真实场景转化为可复用的空间底座，在其上快速编排互动、剧情、导览、营销和运营体验，并能发布到多个项目和终端。

产品升级的核心顺序：

1. **先把真实景区底座产品化**：导入、分块、LOD、碰撞、坐标、版本、性能预算。
2. **再把体验逻辑产品化**：从线性剧情升级为空间体验图和可复用交互组件。
3. **再把资源和项目打通**：景区、底座、素材、模板、体验、发布版本解耦，支持跨项目复用。
4. **最后把商业闭环做完整**：发布、运行、数据、复盘、二次运营，而不止是导出 JSON。

一句话判断：

> 现在适合演示“能不能编辑”，下一阶段要证明“能不能交付、能不能复用、能不能持续赚钱”。

## 2. 当前项目审计

### 2.1 已有能力分层

| 能力层 | 当前实现 | 判断 |
|---|---|---|
| 场景数据 | `scene` 包含 base、objects、sequences、triggers、story、anchors、assets | 已有基础，但仍偏 Demo Schema |
| 编辑器壳层 | 左侧大纲、中间视口、右侧属性、底部内容/时间线/日志 | 已形成可用工作台骨架 |
| 三维对象 | splat_segment、quad、video_quad、glb、light、compound | 足够做演示，缺少可复用语义组件 |
| 高斯底座 | 已引入 `gaussian-splats-3d`，存在 `DropInViewer` 加载路径 | 接入方向已有，距离生产级底座管理仍有较大差距 |
| 互动 | tap、gaze、hold、enter、seq_event、node_done | 已有互动最小闭环，条件和动作仍较少 |
| 时间线 | transform、opacity、video、clip、event 等轨道 | 可支撑演示，缺少模板化、参数化和多人编辑语义 |
| 剧情 | chapter > node，节点可绑定对象和锚点 | 更像线性流程，不足以承载复杂景区体验 |
| 素材 | 本地导入、拖拽生成对象、内置 FX 素材 | 适合黑客松，不能作为团队资产中心 |
| 协作 | Yjs、房间、presence、软锁、撤销 | 已有亮点，需补权限、评论、历史和发布治理 |
| AI | 自然语言生成场景操作，带白名单和别名解析 | 具备差异化，需转为可审计的 Copilot 工作流 |
| 试玩 | 编辑器内桌面模拟、游客视角、相机/陀螺仪方向 | 有验证价值，正式 Runtime 尚未形成 |
| 发布 | 预算检查、引用检查、发布检查、导出 JSON | 目前是“检查并导出”，还不是“构建并部署” |

### 2.2 代码与产品状态中的关键事实

1. `README.md` 仍将真实 SOG 高斯底座标记为待完成，但当前 `viewport.js` 已经存在 `DropInViewer` 和 `addSplatScene` 路径。这说明代码已经迈入接入阶段，但产品文档、验收标准和真实资产链路尚未同步。
2. 当前素材仍明显依赖本地 `ObjectURL`、占位素材和本地存储。它适合单机演示，不适合多个项目、多人团队和长期交付。
3. 当前 `publishCheck` 主要检查引用完整性、节点、资产登记和粗略预算；没有生成真正的运行包、部署目标、运行时能力校验和版本回滚。
4. 当前 AI 已经能改对象、触发器、时间线和节点，但场景内容与编辑器产品能力之间的权限边界仍需要被产品化，例如预览变更、批量确认、差异对比、操作回滚。
5. 当前数据模型以 `objects` 为中心，真实景区项目会需要“场景底座、空间分区、资源、交互组件、体验流程、发布版本、运行数据”等一组稳定实体。

### 2.3 当前项目的真实阶段

建议将当前项目定义为：

> **概念验证完成，编辑器工作台 Beta 雏形，目标是成为景区互动内容生产工具，尚未达到生产交付 MVP。**

它已经可以证明：

- 三维场景可以被编辑；
- 高斯/点云底座可以作为真实景区空间背景接入；
- 互动对象可以被摆放、播放、触发和协作修改；
- AI 可以作为场景编辑入口；
- 编辑器内已经有“布置—编辑—试玩验证”的最小闭环。

后续重点不是先建设游客端数据闭环，而是验证编辑器对景区和运营人员的生产效率：

- 一个景区人员能否理解并完成对象布置；
- 一个运营人员能否不依赖研发修改互动内容；
- 一个制作团队能否将高斯场景、素材和互动逻辑稳定交付；
- 一个项目能否在发布前完成空间、交互、资源和性能检查；
- 同一套空间资源和互动组件能否服务多个项目。

## 3. 产品战略重新定义

### 3.1 产品定位：景区互动空间编辑器

“高斯泼溅”是空间底座技术，不是编辑器的全部定位。当前产品的核心任务是：

> 让景区或运营人员在真实景区的高斯场景上，完成互动元素的布置、编辑、关联、预览和发布。

产品首先服务于编辑和交付，不把游客端使用数据作为当前阶段的北极星。游客端 Runtime 可以作为后续发布目标和验证环境，但不是当前编辑器价值判断的前置条件。

编辑器要解决的是：

- **看得懂**：能看清高斯场景、空间分区、对象和锚点；
- **放得准**：能把互动元素放到真实位置，并保持坐标、锚点和底座版本一致；
- **配得快**：能用组件、模板和动作卡快速完成互动配置；
- **改得稳**：修改素材、文案、动画和触发条件时，不破坏已有引用；
- **验得过**：发布前能检查资源、空间、交互、设备和性能；
- **复用强**：同一景区资源可以服务多个主题、活动和项目。

当前不应把产品描述成“一个可加载高斯模型的三维编辑器”，而应描述成：

> **面向景区与运营团队的真实空间互动内容编辑器。**
>
> 高斯场景负责还原真实空间，编辑器负责在空间上布置可互动内容，并将其整理成可发布的体验场景。

### 3.2 产品价值判断

当前阶段建议用以下指标判断编辑器是否完善：

| 方向 | 核心问题 | 建议指标 |
|---|---|---|
| 布置效率 | 从导入高斯底座到放置第一个互动元素需要多久 | 首次可布置时间；单对象平均布置时间 |
| 编辑效率 | 运营人员能否独立修改内容 | 无研发参与完成的编辑任务比例 |
| 交互表达 | 常见景区互动是否能被组件化表达 | 常用互动模板覆盖率；从空白到可试玩时长 |
| 空间准确性 | 内容是否能稳定绑定真实空间 | 锚点绑定成功率；底座版本迁移成功率 |
| 发布质量 | 场景是否可以安全交付 | 发布阻断项；资源/引用/性能问题发现率 |
| 复用效率 | 资源能否在多个项目复用 | 公共资产复用率；模板复用率 |
| 协作效率 | 团队是否能共同完成交付 | 评论关闭时长；从草稿到审核版本时间 |
| AI 辅助 | AI 是否减少编辑成本 | AI 建议采纳率；AI 修改回滚率 |

### 3.3 产品北极星指标

建议北极星指标调整为：

> **每月成功完成并发布的互动景区场景数。**

这里的“成功完成”必须包含：真实空间底座、互动元素、体验逻辑、资源引用、发布检查和可复现的场景版本，而不是只导出一份静态 JSON。

配套指标：

- **编辑器可用性**：首次布置耗时、常用任务成功率、撤销/恢复成功率；
- **内容生产效率**：互动组件使用率、模板复用率、从空白到试玩的时间；
- **交付稳定性**：发布阻断项、资源加载失败率、底座/锚点引用错误率；
- **协作效率**：多人编辑冲突、评论关闭时长、审核通过周期；
- **商业交付效率**：单个景区项目的交付周期、二次修改成本、跨项目复用比例。

游客端运行数据属于后续 Runtime 和项目运营阶段的增强能力，不作为当前编辑器是否成立的必要条件。

### 3.4 推荐的产品分层

```text
空间资源层
├─ 景区 / 场地
├─ 高斯底座 / SOG / PLY / Mesh / Collider
├─ 空间分区 / 锚点 / 坐标系 / LOD
└─ 原始资产 / 模型 / 图片 / 视频 / 音频 / 特效

体验创作层
├─ 场景编辑器
├─ 空间对象与交互组件
├─ 剧情图 / 导览图 / 任务图
├─ 时间线与行为模板
└─ AI 场景 Copilot

编辑器交付层
├─ 场景编辑器
├─ 编辑器内试玩/预览
├─ 资源、空间、交互和性能检查
└─ 发布包、版本、审核、回滚

资源与协作层
├─ 项目权限与角色
├─ 景区底座与空间资源库
├─ 互动组件与模板中心
├─ 评论、审核、变更记录
└─ 多项目复用与依赖管理

可选运行层
├─ Web / 移动端 / AR Runtime
├─ 线下大屏 / 展陈 Runtime
└─ 游客运行数据与体验分析
```

## 4. 客户与使用场景

### 4.1 建议优先服务的客户

#### A. 景区集团 / 文旅投资方

关心：多个景区统一管理、长期运营、投入产出和品牌统一。

需要：

- 景区资源资产化；
- 多项目复用；
- 统一发布和数据看板；
- 活动、节庆、夜游、研学等不同体验快速上线。

#### B. 景区数字化服务商 / 集成商

关心：交付效率、项目毛利、客户定制和实施风险。

需要：

- 底座和素材标准化；
- 模板化生产；
- 多人协作；
- 可复制交付包；
- 交付后由客户自己改内容而不破坏底层工程。

#### C. 景区内容运营团队

关心：不依赖研发，能否快速更新活动和内容。

需要：

- 低门槛互动编排；
- 审核发布；
- 节点数据；
- 节庆主题替换；
- 资产和模板搜索。

### 4.2 角色与权限

建议至少定义以下角色：

| 角色 | 核心工作 | 需要的权限 |
|---|---|---|
| 平台管理员 | 组织、项目、账单、权限 | 全局管理 |
| 景区管理员 | 管理景区底座和项目 | 项目级管理 |
| 场景设计师 | 摆放对象、编排体验 | 编辑场景内容 |
| 视觉/素材设计师 | 上传、管理和替换资产 | 管理素材，不改逻辑 |
| 技术实施 | 坐标、VPS、性能、Runtime | 管理底座和发布环境 |
| 内容运营 | 修改文案、活动、奖励 | 受限编辑和发布申请 |
| 审核/客户 | 评论、预览、验收 | 只读、评论、批准发布 |

当前“房间 + token + Yjs”的协作方式可以保留为底层能力，但要在产品上升级为项目成员、角色、审核流，而不是让客户理解 room/key。

## 5. 最值得建立的商业壁垒

### 5.1 景区空间底座资产库

高斯重建本身会逐渐普及，真正的壁垒不是“能加载高斯”，而是：

- 同一景区的高质量采集数据；
- 清晰的空间坐标、区域、入口、路径和锚点；
- 可按区域、主题和设备切分的多级底座；
- 与模型、图片、视频、讲解词、历史资料的关联；
- 底座版本和更新记录。

建议把每次采集封装成 `Capture Package`，而不是只存一个 `sog_url`：

```json
{
  "captureId": "capture_xxx",
  "siteId": "site_xxx",
  "source": "gaussian-splatting",
  "format": ["sog", "ply", "collider"],
  "coordinateSystem": "site-local-y-up",
  "bounds": {},
  "chunks": [],
  "lods": [],
  "anchors": [],
  "quality": {},
  "version": "1.0.0"
}
```

### 5.2 空间体验模板库

景区项目的高频需求具有明显共性，不应每次从空白开始：

- 进入景区自动触发；
- 看向某个遗迹触发讲解；
- 点击文物出现图文卡片；
- 沿路线寻找线索；
- 节庆主题换肤；
- 夜游灯光和音效联动；
- 任务完成后获得徽章；
- 角色出场、变身、环绕、消散；
- 导览路线和分支剧情；
- 活动期间限时内容。

建议将这些抽象为可配置的 `Experience Template`，模板不是一条死时间线，而是：

- 输入参数：对象、文案、素材、触发范围、奖励；
- 空间锚点要求；
- 交互逻辑；
- 默认视觉和声音；
- 设备兼容条件；
- 可替换内容槽位。

### 5.3 当前阶段的核心闭环：真实空间 + 互动内容 + 可发布场景

当前产品优先形成编辑器闭环，而不是先建设游客运营数据闭环：

```text
导入/选择景区高斯底座
  ↓
整理空间分区、锚点和可编辑范围
  ↓
布置模型、图片、视频、灯光、特效、音频和交互组件
  ↓
配置触发条件、动作、时间线和剧情/导览节点
  ↓
编辑器内试玩与多人协作检查
  ↓
执行资源、空间、引用、性能和设备检查
  ↓
生成可交付的发布版本
```

游客端 Runtime、运行数据和体验漏斗属于后续扩展：它们可以验证发布结果，但不应反过来定义当前编辑器的主要工作流。

## 6. 编辑器产品升级方案

### 6.1 P0：底座资产化，而不是继续做占位

#### 景区空间资源的分层

空间资源不应只表现为一条 `sog_url`。建议把景区资源拆成可管理、可复用、可检查的资源包：

| 资源类别 | 细分资源 | 主要用途 |
|---|---|---|
| 空间底座 | SOG、PLY、SPZ、Splat、Mesh、Collider | 还原真实场景、碰撞和定位 |
| 底座变体 | 原始采集版、清洗版、轻量版、移动端版、夜景版 | 不同项目、设备和视觉主题 |
| 空间结构 | 区域、房间、道路、入口、出口、可编辑区、禁布区 | 限制布置范围、组织对象 |
| 空间定位 | VPS 锚点、图像/海报锚点、二维码锚点、手动参考点 | 对齐真实空间和内容迁移 |
| 空间辅助 | 地面、墙面、碰撞体、导航路径、触发区域、遮挡体 | 互动、移动、进入和遮挡判断 |
| 几何内容 | GLB/GLTF、角色、建筑构件、文物、植物、道具 | 真实空间上的三维互动元素 |
| 平面内容 | PNG/JPG/WebP、透明贴图、图标、海报、UI 卡片 | 标识、提示、装饰和图文信息 |
| 视频内容 | MP4/WebM、透明视频、全景视频、短片段 | 讲解、出场、特效和沉浸内容 |
| 音频内容 | MP3/WAV/OGG、语音、环境声、音乐、音效 | 导览、反馈、氛围和剧情 |
| 特效内容 | 粒子、序列帧、Shader、光晕、烟雾、火焰、法阵 | 空间氛围、反馈和引导 |
| 交互资源 | 触发器、按钮、手势、注视目标、进入区域 | 让对象具有可操作性 |
| 内容资源 | 标题、正文、讲解词、多语言文本、奖励、任务 | 运营人员可维护的内容 |
| 主题资源 | 色板、字体、材质预设、天空、灯光方案 | 节庆、品牌和项目换肤 |
| 配置资源 | 设备 Profile、性能预算、发布环境、权限策略 | 发布前检查和交付治理 |

建议第一版 `Asset` 增加以下字段：

```json
{
  "id": "asset_xxx",
  "kind": "model|splat|image|video|audio|fx|font|icon|content|template|config",
  "subtype": "glb|sog|transparent-video|voice-over|particle|guide-card",
  "name": "石窟讲解视频",
  "source": "upload|generated|built-in|linked",
  "variants": {
    "desktop": "asset_variant_xxx",
    "mobile": "asset_variant_xxx",
    "low": "asset_variant_xxx"
  },
  "metadata": {
    "bytes": 0,
    "duration": 0,
    "width": 0,
    "height": 0,
    "triangleCount": 0,
    "splatCount": 0,
    "hasAlpha": false,
    "language": "zh-CN"
  },
  "tags": ["花果山", "讲解", "入口"],
  "license": "project|site|organization|third-party",
  "version": "1.0.0"
}
```


#### 当前问题

当前底座主要体现为 `base.sog_url` 和可视化加载入口，缺少面向生产的底座管理语义。高斯模型如果没有分块、LOD、碰撞和空间坐标，后续互动内容会全部绑在临时坐标上，项目越大越难维护。

#### 建议升级

新增“空间底座管理”模块：

1. 底座导入：SOG、PLY、SPZ、视频抽帧、Mesh、Collider。
2. 自动分析：包围盒、尺寸、原点、地面、可见区域、文件体积、预计 GPU 占用。
3. 空间分块：按区域或网格切分 splat segment。
4. LOD：近景、中景、远景分级加载。
5. 碰撞层：从底座生成或绑定 Collider，支持地面、墙体、路径区域。
6. 坐标校准：平移、旋转、缩放、参考点和坐标系说明。
7. 锚点管理：VPS、图像锚点、入口点、讲解点、任务点。
8. 版本管理：原始采集版、清洗版、发布版、回滚版。
9. 预览诊断：加载时间、显存、帧率、可见分块和网络请求。

#### 验收标准

- 新建一个景区项目后，底座可以被导入、预览、分区和绑定锚点。
- 同一个底座可以创建多个体验项目，而不是复制一份大文件。
- 底座换版本时，体验对象通过稳定锚点和区域 ID 自动迁移或提示冲突。
- 在目标设备上能看到真实的加载耗时、FPS 和资源占用，而不是只显示估算值。

### 6.2 P0：从“对象”升级为“组件”

当前 `objects` 足够表达“放一个东西”，但无法很好表达“一个可复用的互动景点单元”。建议保留对象作为底层实体，在其上增加组件化语义：

```text
ExperienceObject
├─ TransformComponent
├─ RenderComponent
├─ SpatialComponent（区域、锚点、地面关系）
├─ InteractionComponent（点击、注视、进入、手势）
├─ TimelineComponent
├─ ContentComponent（标题、讲解词、多语言）
├─ AnalyticsComponent（曝光、触发、完成）
└─ AvailabilityComponent（设备、时间、活动条件）
```

建议优先抽象以下对象/组件：

- 讲解点；
- 互动展品；
- 入口触发区；
- 路线节点；
- 视频/图片卡片；
- 角色/模型；
- 粒子与灯光效果；
- 奖励/徽章；
- 音频导览；
- 任务目标。

这样设计师编辑的是“互动景点”，而不是需要理解 `video_quad + trigger + sequence + card` 的底层组合。

### 6.3 P0：剧情树升级为空间体验图

当前 `chapter > node > next` 是好的第一版，但它只能表达简单线性流程。景区体验通常需要：

- 多入口；
- 条件分支；
- 可选任务；
- 任务未完成时的回退；
- 逛到不同区域后触发不同内容；
- 同一节点重复触发但奖励只发一次；
- 多条路线最终汇聚；
- 节庆期间替换一段内容。

建议数据模型升级为：

```text
Experience
├─ EntryPoints[]
├─ SpatialZones[]
├─ FlowNodes[]
│  ├─ trigger
│  ├─ conditions
│  ├─ actions
│  ├─ state changes
│  └─ analytics event
├─ Branches[]
├─ Rewards[]
├─ Localization[]
└─ CompletionRules
```

编辑器上增加“体验图”视图，与“场景对象树”并列：

- 场景视图：解决“空间里有什么”；
- 体验图视图：解决“游客怎么经历”；
- 底座视图：解决“真实空间怎么定位”；
- 资源视图：解决“哪些内容可复用”。

### 6.4 P1：时间线从动画工具升级为行为编排器

当前时间线已经可以支撑变换、透明度、视频和事件。下一步不要只增加更多轨道，而要增加“行为级模板”：

- 出场；
- 讲解开始/结束；
- 镜头引导；
- 音频播放；
- 震动/提示；
- 计分/奖励；
- 进入下一节点；
- 多对象并行；
- 可重复/只执行一次；
- 按设备能力降级。

动作卡应由固定动作名称升级为带参数的组件，例如：

```text
「讲解点」
├─ 触发：进入半径 3m
├─ 展示：标题 + 图片 + 文案
├─ 播放：音频
├─ 动效：目标对象高亮
├─ 完成：播放结束或点击继续
└─ 记录：讲解点曝光 / 完成
```

### 6.5 P1：内容与空间解耦

当前对象直接保存 `asset`，节点直接保存 `anchor`，随着项目增长会出现“素材换了导致逻辑断裂”“底座换了导致所有位置失效”的问题。

建议使用稳定引用：

- `assetId`：引用资产，不直接引用本地 URL；
- `anchorId`：引用空间锚点；
- `zoneId`：引用空间区域；
- `prefabId`：引用可复用组件；
- `experienceId`：引用体验逻辑；
- `releaseId`：引用已发布版本。

本地临时 URL 只能存在于缓存层，不能作为生产数据源。

### 6.6 P0：发布不是导出 JSON，而是构建可交付场景包

发布流程建议变成：

```text
编辑草稿
  ↓
结构检查
  ↓
资源检查
  ↓
空间定位检查
  ↓
设备能力检查
  ↓
性能预算检查
  ↓
体验预览
  ↓
审核
  ↓
构建 Runtime 包
  ↓
灰度发布
  ↓
正式发布 / 回滚
```

发布包应包含：

- 场景和互动体验数据；
- 资源 manifest 和资源变体；
- 高斯底座、空间分区、锚点和 Collider 版本；
- 编辑器 Schema 版本；
- 目标 Runtime/预览能力说明（可选）；
- 设备 Profile 和性能预算；
- 多语言内容和主题配置；
- 发布环境配置；
- 版本号、依赖关系和回滚信息。

`publishCheck` 应扩展为四类：

1. **结构阻断**：ID、引用、节点、动作不完整。
2. **空间阻断**：缺少锚点、越界、碰撞缺失、坐标异常。
3. **运行阻断**：目标 Runtime 不支持某种材质、视频、交互或定位方式。
4. **性能警告/阻断**：资源体积、显存、视频路数、加载时间、FPS 超预算。

## 7. 跨项目互通与协同设计

### 7.1 建议的组织结构

```text
Workspace（集团/公司）
└─ Site（景区/场地）
   ├─ Capture（空间采集版本）
   ├─ Asset Library（景区公共素材库）
   ├─ Project（一个主题或活动项目）
   │  ├─ Experience（游客体验）
   │  ├─ Drafts（草稿）
   │  ├─ Releases（发布版本）
   │  └─ Analytics（运行数据）
   └─ Shared Templates（景区级模板）
```

关键原则：

- **Site 是真实空间的唯一归属**；
- **Capture 是空间底座的版本**；
- **Project 是业务主题和交付项目**；
- **Experience 是可运行的游客体验**；
- **Asset/Template 可以跨 Project 复用**；
- **Release 是一份可部署、可回滚的快照**。

### 7.2 复用等级

| 等级 | 复用内容 | 例子 |
|---|---|---|
| L1 | 原子素材 | 图片、视频、GLB、音频、特效 |
| L2 | 空间对象 | 一个讲解牌、一个角色、一个灯光效果 |
| L3 | 互动组件 | 点击弹卡、进入触发、寻找线索 |
| L4 | 体验模板 | 夜游导览、研学任务、节庆打卡 |
| L5 | 项目方案 | 某景区完整的“西游主题导览” |

每个复用实体都需要：

- 版本号；
- 来源项目；
- 依赖列表；
- 适用底座/区域；
- 目标设备；
- 授权范围；
- 更新策略。

### 7.3 资产变更策略

项目互通最容易出问题的地方不是复制，而是升级：

- 公共模型更新后，哪些项目自动更新；
- 项目是否允许覆盖公共素材；
- 底座新版本发布后，旧项目是否锁定旧底座；
- 模板升级后，已发布项目是否跟随；
- 资源被删除时，哪些项目会受影响。

建议默认采用：

> **发布版本锁定依赖，草稿可选择跟随更新。**

通过依赖图提前提示影响范围，不允许直接静默替换。

## 8. AI 产品化方向

当前 AI 操作白名单是正确方向，但还可以从“聊天改场景”升级为“可审计的空间创作 Copilot”。

### 8.1 AI 的四类工作模式

1. **生成**：根据自然语言创建互动景点、动作和剧情节点。
2. **理解**：解释场景结构、定位断链、分析性能和体验流程。
3. **转换**：把策划文案转换为节点、触发器、时间线和多语言内容。
4. **优化**：提出空间布局、交互完成率、资源体积和设备兼容性建议。

### 8.2 AI 不应该直接静默修改生产场景

推荐流程：

```text
用户意图
  ↓
AI 读取结构化场景摘要
  ↓
生成 Plan / Ops
  ↓
显示变更预览和影响范围
  ↓
用户确认
  ↓
事务性执行
  ↓
可回滚、可审计、可协作同步
```

每次 AI 操作应记录：

- 原始输入；
- 使用的场景版本；
- 生成的操作列表；
- 成功/失败项；
- 用户是否确认；
- 回滚关系；
- 产生的资源和成本。

### 8.3 优先做的 AI 能力

- “把这个区域做成 5 分钟夜游体验”；
- “检查这个体验为什么无法发布”；
- “找出所有没有锚点的节点”；
- “将这份导览稿变成体验图”；
- “把当前体验适配到低端手机”；
- “给这个景区生成 3 套节庆主题”；
- “将同一体验复制到另一个底座区域并提示坐标冲突”。

这些能力比单纯“放一个橙色点光源”更接近商业价值。

## 9. 技术产品化建议

### 9.1 场景文件需要版本化 Schema

当前场景结构已经能支撑 Demo，但后续必须加入：

```json
{
  "schemaVersion": "2.0.0",
  "projectId": "project_xxx",
  "siteId": "site_xxx",
  "baseId": "capture_xxx",
  "experienceId": "experience_xxx",
  "dependencies": [],
  "entities": {},
  "runtime": {},
  "analytics": {},
  "release": {}
}
```

要求：

- 所有实体使用稳定 ID，避免使用带中文语义的 ID 作为生产规范；
- Schema 支持迁移脚本；
- 草稿、快照、发布版本不可混用；
- 文件中只保存资源引用，不保存不可复用的临时 URL；
- 大型底座和视频不嵌入场景 JSON。

### 9.2 性能预算必须从估算变成实测

当前 `budget()` 的 bytes、videos、tris、estFps 作为早期提醒是有价值的，但不应作为最终依据。高斯场景更需要关注：

- GPU 显存；
- splat 数量和可见 splat 数；
- 分块数量；
- 首屏加载时间；
- 网络并发请求数；
- 视频解码路数；
- 纹理内存；
- 移动端温度和持续帧率；
- Runtime 内存回收。

建议增加真实设备 Profile：

- Desktop High；
- Desktop Standard；
- iPhone/高端 Android；
- 中端 Android；
- 线下大屏。

每次发布前在目标 Profile 上生成报告：

```text
首屏加载：4.8s
稳定帧率：58 FPS
峰值显存：1.3 GB
视频路数：2/3
可见 splat：1.8M
风险：中端 Android 峰值显存超限
建议：远景切换 LOD-2，延迟加载视频 B
```

### 9.3 Runtime 是发布目标，不是当前编辑器的主战场

编辑器内试玩/预览是当前必须完善的能力，用于验证：

- 对象是否放置准确；
- 互动条件和动作是否符合预期；
- 时间线、剧情节点和资源引用是否完整；
- 发布前是否存在明显的空间和性能问题。

游客端 Web/移动端/AR Runtime 可以独立建设，作为后续发布目标。它不应反向污染编辑器的数据模型和主界面，也不应成为当前阶段判断编辑器功能完善度的唯一标准。

编辑器与 Runtime 之间只通过版本化的发布包衔接：

```text
Editor Draft → Preview Validation → Release Package → Optional Runtime
```

### 9.4 协作从“多人同时改”升级为“团队交付流程”

Yjs 负责实时同步是合适的，但产品还需要：

- 评论定位到对象、节点、时间线关键帧；
- 草稿、待审核、已批准、已发布状态；
- 变更历史和对象级历史；
- 审批人和发布人；
- 只读客户链接；
- 复制项目和分支实验；
- 版本差异对比；
- 离线编辑冲突处理；
- 资产和底座权限隔离。

## 10. 路线图与优先级

### 阶段 0：从 Demo 收敛为产品契约（1–2 周）

目标：停止继续堆演示功能，先稳定数据和交付边界。

重点：

- 冻结第一版 Schema，并加 `schemaVersion`；
- 清理 `sog_url`、临时 URL、资产 ID 等引用规则；
- 明确 Site、Capture、Project、Experience、Release 五类核心实体；
- 统一对象、节点、触发器、时间线的 ID 规范；
- 建立真实资产 manifest；
- 将文档中的“待完成能力”和代码中的实际能力对齐；
- 增加基础测试：Schema 校验、发布检查、导入导出、引用迁移。

**阶段出口：** 任意场景都能被导出、重新导入、校验、迁移，并且不会依赖本机 localStorage 才能运行。

### 阶段 1：生产 MVP（3–6 周）

目标：完成“景区底座 → 互动元素布置 → 体验编辑 → 可发布场景包”的最小闭环。

重点：

- 底座导入和资产 manifest；
- 高斯分块、LOD、碰撞和坐标校准；
- 空间区域和锚点；
- 讲解点、互动展品、入口触发、任务点等组件；
- 体验图视图；
- 参数化动作模板；
- 发布包构建和版本号；
- 编辑器内试玩/预览模式；
- 可交付场景包和版本管理；
- 目标设备性能报告；
- 对象和节点的评论、审核状态。

**阶段出口：** 一个景区或运营人员可以基于真实高斯底座，独立完成互动元素布置、交互编辑、预览、审核和发布。

### 阶段 2：商业试点（6–10 周）

目标：交付给 1–2 个景区或文旅服务商，验证编辑器的交付效率和跨项目复用。

重点：

- VPS/图像锚点/海报兜底；
- 可选的 Web/移动端 Runtime 对接；
- 发布包在目标设备上的验证；
- 可选的游客运行数据和体验分析；
- 多项目资源库；
- 项目角色和权限；
- 版本回滚和灰度发布；
- AI 计划预览、确认和审计；
- 体验模板中心。

**阶段出口：** 能回答“运营人员是否能独立编辑、哪些互动组件最常用、同一套资源能否快速复制到新项目、发布风险是否可控”。

### 阶段 3：平台化（3–6 个月）

目标：从定制项目工具升级为可复制的平台。

重点：

- 多景区 Workspace；
- 景区公共资产库和授权；
- 模板市场/内部模板中心；
- 体验 A/B 测试；
- 多语言和多品牌主题；
- 大屏、Web、移动 AR 等多 Runtime；
- 批量复制体验到多个区域；
- 自动性能优化和设备适配；
- AI 场景诊断和自动改版建议；
- 项目成本、用量、收益数据。

### P0：不做就无法商业交付

- 体验图；
- 互动景点组件；
- 参数化动作卡；
- 多项目资源库；
- 模板中心；
- 可选的游客运行数据和体验分析；
- AI Plan/Preview/Apply/Audit；
- 底座版本迁移和影响分析；

### P2：扩大商业边界

- 模板市场；
- A/B 测试；
- 多语言和品牌主题；
- 大屏、线下展陈和更多 Runtime；

- 大量新增单次使用的特效类型；

- 没有真实 Runtime 支撑的复杂 AR UI；
- 没有埋点和模板化的更多剧情卡片；
- 只扩大聊天能力、不增加可审计性的 AI 指令；
- 继续扩展本地 localStorage 能力。

## 12. 商业化建议

### 12.1 第一阶段：项目制切入

适合通过景区资源和交付能力快速拿到试点：

- 景区空间数字化；
- 一个主题体验项目；
- 一套可交付的互动场景发布包；
- 一套编辑器内试玩/预览和审核流程；
- 一定数量的互动组件、模板和景区资源。

销售重点不是“卖编辑器”，而是卖：

> 在固定周期内，将一个景区区域变成可上线的沉浸式体验，并且后续内容可以由客户自己持续更新。

### 12.2 第二阶段：平台订阅/服务费

可以按以下维度组合报价：

- 景区/场地数量；
- 空间底座容量；
- 编辑器席位；
- 景区空间底座容量和资源用量；
- 发布环境/项目数量；
- 协作、审核和版本管理能力；
- 可选 Runtime 对接与运营服务；
- 高级 AI 和模板能力。

### 12.3 第三阶段：资产和模板生态

当跨项目复用稳定后，可以发展：

- 景区专属资产包；
- 主题体验模板包；
- 专业供应商素材入驻；
- 采集、建模、动效、讲解、运营服务市场；
- 资产授权和分成。

## 13. 主要风险与应对

| 风险 | 表现 | 应对 |
|---|---|---|
| 过度依赖单个高斯格式 | 供应商、设备、Runtime 受限 | 建立 Capture Package 抽象，不把 SOG 当业务模型 |
| 底座更新导致内容失效 | 锚点和对象漂移 | 稳定 Anchor/Zone ID + 版本迁移 + 冲突报告 |
| 编辑器没有稳定发布能力 | 能布置，不能交付 | 发布包、预览检查和版本回滚列为 P0 |
| 本地素材不可持久化 | 换电脑、协作、发布失败 | 资产服务、manifest、缓存和 CDN |
| 性能估算不准确 | 手机上卡顿或崩溃 | 真实设备 Profile 和发布前实测 |
| AI 误改生产内容 | 用户不信任 | Plan/Preview/Confirm/Audit/Rollback |
| 协作只解决同步 | 项目仍无法验收 | 角色、评论、审核、版本和发布状态 |
| 定制项目过重 | 每个景区重新开发 | 组件、模板、资产复用和项目复制 |
| 高斯视觉效果不稳定 | 采集质量影响体验 | 采集质检、底座版本、质量评分和降级方案 |

## 14. 推荐的第一个真实试点

不建议第一单就做“全景区、全 AR、全功能”。建议选择一个边界清晰的区域，形成可以复制的标杆：

### 试点范围

- 一个入口或一条 100–300 米游览路线；
- 一个高斯底座；
- 3–5 个稳定锚点；
- 5 个互动景点；
- 1 条主线体验 + 1 个支线任务；
- 3 类对象：真实空间分块、角色/模型、图文/视频卡片；
- 1 套编辑器内预览/试玩流程；
- 1 个 Web 编辑和审核后台；
- 可选的 Runtime 发布适配，不作为本阶段前置。

### 试点体验示例

```text
进入入口
  → 看到空间遗迹高亮
  → 走近触发讲解
  → 注视虚拟角色 1 秒
  → 角色出场并播放音频/视频
  → 在下一个锚点寻找符号
  → 完成任务获得徽章
  → 数据记录完成率和每个节点停留时间
```

### 试点必须交付的结果

- 编辑团队能自己修改文案和素材；
- 技术团队能替换底座版本并看到影响范围；
- 客户能通过链接预览和评论；
- 版本能发布、回滚；
- 场景包能在目标发布环境中完成资源和性能验证；
- 编辑器能明确展示空间、交互、资源和性能风险；
- 下一条路线可以复用已有模板，而不是重新开发。

## 15. 最终建议

### 产品层

把目标从“做一个好看的虚拟场景编辑器”升级为：

> **把真实景区变成可持续生产、可复用、可发布的互动空间体验。**

### 研发层

优先建立稳定的数据契约、底座资源层、互动组件、预览验证和发布系统；不要先继续增加视觉 Demo 数量。

### 商业层

先以景区真实试点证明编辑器的交付效率、内容复用和运营人员自主修改能力，再把通用能力沉淀为平台订阅、模板和资产复用。

### 资源层

景区资源的核心价值不只是“有模型”，而是形成：

- 景区空间底座；
- 空间分区、锚点和碰撞辅助；
- 文化内容与讲解素材；
- 模型、图片、视频、音频和特效；
- 互动组件与体验模板；
- 跨项目可复制方案。

### 下一步最推荐的三个动作

1. **冻结并重构产品 Schema**：明确 Site、Capture、Project、Experience、Release，并实现版本迁移。
2. **选一个真实景区区域做编辑器端到端试点**：从高斯底座导入开始，到互动布置、体验编辑、预览、审核和发布结束。
3. **用试点结果反推产品优先级**：以“首次布置时长、从空白到可试玩时长、发布成功率、模板复用率和运营人员独立完成率”替代“功能数量”作为判断依据。

## 16. 编辑器统一设计系统

编辑器后续所有新增界面、组件和交互都必须遵循独立的设计系统，不再由各模块临时决定颜色、间距、圆角、按钮样式或图标。

设计系统文件：

- [`docs/xujing-editor-design-system.md`](xujing-editor-design-system.md)：设计原则、Design Token、组件目录、页面模板和验收规则；
- [`docs/design-tokens.json`](design-tokens.json)：可被代码和设计工具读取的 Token 源文件。

设计方向：

> **真实空间工作台 × 瓷白面板 × 橙色行动色 × 冷蓝信息色**

原则：

1. 编辑器优先保证空间内容的可读性，界面不与高斯场景争夺视觉注意力；
2. 橙色只表达当前操作、选中、主操作和重要引导，不大面积装饰；
3. 蓝色表达信息、链接和辅助状态；绿色表达通过/完成；黄色表达警告；红色只表达错误、阻断和危险操作；
4. 所有 UI 图标统一使用 Remix Icon，禁止继续新增 Emoji、随机 Unicode 符号和自绘不一致图标；
5. 所有布局遵循 4px 基础网格，常用间距优先使用 4/8/12/16/24/32；
6. 组件必须同时定义默认、悬停、按下、选中、禁用、错误和加载状态；
7. 复杂功能优先沉淀为组件和页面模板，再在业务模块中组合使用。

第一批需要统一的区域：

- 顶栏：品牌、场景名、保存状态、编辑/试玩、协作、预览、发布；
- 左侧大纲：内容/世界大纲、搜索、章节、互动对象、资源分组；
- 中间视口：工具栏、Gizmo、对象标签、空间锚点、视口状态；
- 右侧属性：对象头部、状态 Chip、分组卡片、字段、触发器句式；
- 底部 Dock：资源浏览器、时间线、日志、预算状态；
- 弹窗和反馈：发布检查、错误、确认、Toast、空状态、加载状态。

**设计系统是后续开发的前置约束，而不是上线前的视觉补丁。**

| 判断项 | 结论 |

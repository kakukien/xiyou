04 / Draft → Release → Runtime

现场新增：让手机真正看到发布结果

推荐演示 现场手机扫码

这一段紧接在多人协作之后：先在编辑器里加一个方块并发布，再用手机扫码进入独立的游客 Runtime。用它明确说明“试玩不是游客端”，也说明发布后新旧会话为什么不一定同时强制刷新。

2. 等待手机扫码

新会话读取 active Release；已打开的会话不会直接读取 Draft。

入口

二维码、短链接或 NFC 只负责打开体验，不携带整份场景 JSON。正式环境建议使用短码解析 Experience。

QR / LINK / NFC → Experience Resolver

定位

扫码后仍要完成空间校准。QR/图像锚点适合 MVP，VPS 适合后续自然化的景区体验。

GPS = 粗定位 · VPS = 精定位

06 / Awareness design

鼠标、用户名和角色颜色

鼠标位置和在线身份属于临时状态，不应该写入场景文档。推荐通过 Yjs Awareness 广播，场景编辑内容继续走 Yjs 文档。

管理者

橙色。负责介绍项目、观察成员和发布检查。

role: manager · #F97316

编辑者

蓝色。负责移动对象、添加素材和修改场景。

role: editor · #2563EB

预览者

绿色。负责观察场景、切换试玩和反馈效果。

role: previewer · #16A34A

随机访客名

每个浏览器首次进入时生成 6～8 位大写字母数字名称，避开容易混淆的 I / O / 0 / 1。名称可以保存在 localStorage，刷新后保持不变。

const chars = 'ABCDEFGHJKLMNPQRSTUVWXYZ23456789'
const bytes = crypto.getRandomValues(new Uint8Array(6))
const name = Array.from(bytes, b => chars[b % chars.length]).join('')

示例：A7K2M9 · Q8P4DX · N3W7F2K

Awareness 数据

{
  name: 'A7K2M9',
  role: 'editor',
  color: '#2563EB',
  cursor: { x: 0.42, y: 0.58, visible: true },
  sel: ['glb_wukong']
}

x / y 使用 0～1 相对坐标，不同步屏幕像素。

为什么不用像素坐标？ 每个人的浏览器窗口大小不同。把鼠标位置记录成 Viewport 的相对比例，其他设备才能正确渲染。建议鼠标移动事件节流到每秒 20～30 次。

08 / Recovery

故障排查

现场不要反复刷新所有设备。先判断是 HTTP 网站问题、WebSocket 连接问题、房间参数问题，还是本地缓存覆盖问题。

网页能打开，但显示“未连接”

先检查完整链接是否包含正确的 room 和 key，再检查浏览器 Network 面板中的 WebSocket 是否使用 wss://<部署域名>/xiyou-yjs。如果 HTTP 正常而 WSS 不通，通常是代理 Upgrade、Cloudflare Tunnel 或现场网络问题。

排查顺序
1. room / key　→　2. wss 地址　→　3. 协作容器　→　4. 反向代理　→　5. 现场网络
在线人数增加，但场景不一致

先确认所有浏览器使用完全相同的房间名；然后检查是否有人打开了 ?reset=1，以及旧的 localStorage 是否覆盖了云端场景。暂停操作后，由主持人导入备份 scene.json，再让其他人刷新。

鼠标能显示，但挡住了本地点击

光标层和每个协作者鼠标都必须使用 pointer-events: none。它们是视觉 Overlay，不能参与交互命中。

.collab-cursors, .collab-cursor { pointer-events: none; }
所有人显示同一个随机名称

通常是多个标签页共用了同一个浏览器的 localStorage。改用不同浏览器、无痕窗口或不同设备；也可以清除 xiyou.guest.name 后重新进入。

服务器重启后场景丢失

这通常意味着当前 Yjs 服务只在内存中保存文档，或者持久化未正确配置。现场不要主动重启容器；使用主持人的 JSON 备份恢复。正式版本必须补充 Yjs 持久化和场景快照。

手机扫码后看不到刚发布的方块

先确认扫的是“游客 Runtime”二维码，而不是编辑器协作链接；再确认发布成功、手机加载的是 release=v2 或当前 active release，而不是本机 localStorage。如果仍是旧版本，检查 CDN 缓存和 Release API，不要直接把手机接入 Yjs Draft。

正确语义
编辑器 Draft → 发布 v2 → 手机新会话加载 v2
不是
编辑器 Draft → 另一台手机直接读取本机 localStorage
手机打开了 Runtime，但方块没有和真实空间对齐

不要只依赖 GPS 做精确 AR 对齐。GPS 只判断“到了景区/区域”；请让用户扫描入口 QR/图像锚点，或接入 VPS 返回 site-local 坐标。确认锚点物理尺寸、坐标系、朝向和编辑器底座版本一致。

发布 v3 后已经打开的手机没有自动变化

这是默认的安全语义：新会话直接加载 v3，旧会话继续使用当前 Session 的 v2。演示时点击“更新提示”，再由手机用户确认刷新。只有文案、显隐和简单动画等白名单内容适合后续做热更新；底座、锚点、Collider 和剧情结构变更应提示刷新。

09 / Build next

从当前版本继续开发

黑客松现场先证明一条端到端链路：多人一起编辑 Draft，发布成 Release，手机通过二维码进入 Runtime。账号、VPS 和热更新可以在这条链路稳定后继续补齐。

现在就做：现场端到端版

  1. 修复复制协作链接，让邀请链接包含正确的 room + key。
  2. 稳定多人 Draft、角色、Awareness 和协作者鼠标。
  3. 用真实“方块”作为发布演示对象，补齐发布检查和 QR 入口。
  4. 增加独立游客 Runtime 链接，不让手机读取本机 localStorage。
  5. 先支持 QR/图像锚点校准，GPS 仅做粗定位兜底。
  6. 现场明确演示：新会话加载新 Release，旧会话提示更新。

后续再做：商用版

  1. 账号登录和 /auth/me。
  2. 工作空间、项目和成员角色。
  3. 邀请链接和申请加入审批。
  4. 短期协作 Ticket 替换长期 key。
  5. WebSocket 服务端按用户和项目鉴权。
  6. Yjs 持久化、场景快照、发布版本和回滚。
  7. 对象存储替换本地 Blob URL。
不要混淆演示角色和正式权限：通过 URL 的 ?role=manager 只适合现场标识颜色，用户可以自行修改它。正式权限必须由“账号 → 项目成员关系 → 服务端鉴权 → 短期协作 Ticket”完成。

实时层

Yjs 文档和 Awareness。负责在线同步对象、触发器、时间线、头像和鼠标。

Yjs = real-time collaboration

持久层

PostgreSQL、Yjs 持久化和场景快照。负责服务重启、跨设备恢复和版本管理。

Snapshot = durable data

发布层

发布检查、不可变 Release 和回滚。负责让预览或游客端拿到稳定版本。

Release ≠ draft
10 / After the demo

演示结束后

立即处理

  • 导出演示房间最终场景。
  • 确认没有误改正式项目。
  • 保存截图和现场日志。
  • 记录现场使用的房间和 key。

活动结束后

  • 撤销或更换 hackathon-demo 的 key。
  • 清理临时邀请链接和访客房间。
  • 检查服务器磁盘空间。
  • 将有价值的场景复制到正式项目。
  • 不要长期复用现场共享 key。
